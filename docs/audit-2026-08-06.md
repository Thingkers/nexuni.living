## ১. P0 — এখনই বন্ধ করতে হবে (Critical)

### P0-1 · Self-signup দিয়ে যে কেউ Admin হতে পারে

**কোথায়:** `public.profiles` INSERT policy + `guard_profiles_privileged_fields` trigger

**প্রমাণ:**
```
pg_trigger: guard_profiles_privileged_fields | profiles | events=UPDATE | timing=BEFORE
column_privileges: authenticated INSERT → (... role, is_verified, verification_status ...)
pg_policies:  profiles INSERT with_check = (auth.uid() = id)   ← কোনো column restriction নেই
```

`20260702130000_guard_profile_privilege_fields.sql` privilege escalation
আটকায় — কিন্তু trigger-টি **`BEFORE UPDATE` only**। INSERT path সম্পূর্ণ
অরক্ষিত, আর `authenticated`-এর `role` column-এ INSERT grant আছে।

**বাস্তব attack (৩০ সেকেন্ড, কোনো টুল লাগে না):**
1. `/auth/register` দিয়ে normal signup → session পাওয়া যায়
2. App-এর profile insert না করে সরাসরি:
   `POST /rest/v1/profiles` body `{"id": "<my-uid>", "role": "admin",
   "verification_status": "approved", "is_verified": true, ...}`
3. RLS check `auth.uid() = id` — pass। Trigger fire করে না (INSERT)।
4. আক্রমণকারী এখন global admin: `admin_list_profiles()` দিয়ে সব user-এর
   email/phone/bkash/student ID card পড়তে পারে, `/api/admin/delete-user`
   দিয়ে যে কারো account মুছতে পারে, `/api/admin/update-user` দিয়ে অন্যদের
   admin বানাতে পারে।

**Severity:** Critical — সম্পূর্ণ platform takeover, unauthenticated
attacker থেকে শুরু করে।

**Fix:** INSERT trigger যোগ করে privileged column গুলো force করা
(`role := 'student'`, `verification_status := 'pending'`,
`is_verified := false`), এবং `authenticated`/`anon` থেকে ওই তিন column-এ
INSERT/UPDATE grant revoke করা। দীর্ঘমেয়াদে profile row-টা
`auth.users` trigger (`on auth.users insert`) থেকে server-side তৈরি হওয়া
উচিত, client insert থেকে নয়।

### P0-2 · ২৫ জন student-এর ID Card এই মুহূর্তে public internet-এ

**কোথায়:** `storage.buckets` + `src/app/auth/register/page.tsx:uploadIdCard`

**প্রমাণ:**
```
storage.buckets: student-id-cards | public = TRUE | file_size_limit = NULL | allowed_mime_types = NULL
storage.objects: student-id-cards → 25 objects, 25 distinct owners, 1.58 MB
object path সব একই: "<profile-uuid>/id-card.webp"
compressImage() সবসময় .webp বানায় → extension deterministic
anon column grant: profiles → SELECT (id, full_name, university, phone, ...)
storage policy "Allow users to read own id cards": using (bucket_id = 'student-id-cards')
   ← "own" নাম হলেও owner check নেই; যেকোনো authenticated user সব পড়তে পারে
```

**বাস্তব attack (সম্পূর্ণ unauthenticated):**
1. `GET /rest/v1/profiles?select=id` — anon-এর `id` column-এ grant আছে,
   RLS policy `qual: true`। সব user-এর uuid পাওয়া গেল।
2. প্রতিটি uuid দিয়ে
   `GET /storage/v1/object/public/student-id-cards/<uuid>/id-card.webp`
   — bucket `public = true`, তাই কোনো auth লাগে না, RLS-ও bypass হয়।
3. প্রতিটি বাংলাদেশি student ID card-এ থাকে: পূর্ণ নাম, ছবি, student ID,
   university, প্রায়ই জন্মতারিখ/blood group।

`owners = 25` কিন্তু `profiles = 6` — অর্থাৎ **১৯টি ID card এমন
account-এর যেগুলো ইতিমধ্যেই delete করা হয়েছে**।
`/api/admin/delete-user` route profile আর auth user মোছে, কিন্তু storage
object কখনো মোছে না → account delete করার পরেও PII রয়ে যায়।

**Severity:** Critical — চলমান PII breach। বাংলাদেশে identity theft ও
NID-linked জালিয়াতির সরাসরি উপাদান।

**Fix:**
1. **এখনই (manual, dashboard-এ):** bucket-টি private করা।
2. ID card দেখার একমাত্র পথ হবে short-lived **signed URL**, যা শুধু admin
   verification screen server-side ইস্যু করবে।
3. Path-এ unguessable suffix (`<uuid>/<random>.webp`)।
4. Bucket-এ `file_size_limit` + `allowed_mime_types` set করা (চারটি
   bucket-এর কোনোটিতেই এখন নেই)।
5. Account deletion-এ storage cleanup যোগ করা + বিদ্যমান ১৯টি orphan মোছা।
6. Verification approve হয়ে যাওয়ার পরে ID card retention window (যেমন ৩০
   দিন) শেষে auto-delete — কারণ approve হওয়ার পরে ছবিটা রাখার আর কোনো
   business কারণ নেই।

### P0-3 · যে কেউ, login ছাড়াই, সব profile-এর university বদলে দিতে পারে

**কোথায়:** `public.admin_backfill_university_suggestion()` — কোনো tracked
migration-এ নেই, dashboard থেকে তৈরি।

**প্রমাণ:**
```sql
CREATE FUNCTION public.admin_backfill_university_suggestion(p_normalized_text text, p_university_id uuid)
 RETURNS bigint LANGUAGE plpgsql SECURITY DEFINER SET search_path TO 'public'
AS $$ begin
  update public.profiles set university_id = p_university_id
  where university_id is null and lower(trim(university)) = p_normalized_text;
  ...
end $$;
```
```
proacl: postgres=X | anon=X | service_role=X      ← anon-এর EXECUTE আছে
function body-তে কোনো admin check নেই            ← নামে "admin", আচরণে নয়
```

সহোদর function গুলো (`admin_list_profiles`, `admin_list_university_suggestions`,
`admin_list_dismissed_university_suggestions`) সবগুলো ভেতরে
`if not exists (... role = 'admin') then raise exception 'admin only'` করে।
**এই একটাই বাদ পড়েছে** — আর এটাই একমাত্র function যেটা **write** করে।

**বাস্তব attack:** `POST /rest/v1/rpc/admin_backfill_university_suggestion`
anon key দিয়ে (anon key public, browser bundle-এ আছে) →
SECURITY DEFINER হওয়ায় RLS সম্পূর্ণ bypass → পুরো user base-এর
`university_id` ইচ্ছেমতো বদলে দেওয়া যায়। Rate limit নেই, তাই এটি
data-vandalism ও DoS দুটোই।

> এই finding-টি **inspection দিয়ে confirm করা হয়েছে, exploit চালিয়ে নয়** —
> production data mutate করা হয়নি।

**Severity:** Critical — unauthenticated write, RLS bypass।

**Fix:** `revoke execute ... from anon, authenticated` + function body-তে
admin guard যোগ করা, এবং একটি tracked migration-এ নিয়ে আসা।

### P0-4 · যেকোনো logged-in user সবার email, bKash, Nagad, Student ID পড়তে পারে

**কোথায়:** live `profiles` column grants — repo-র migration-এর সাথে drift।

**প্রমাণ:**
```
migration 20260702180000_lock_down_authenticated_sensitive_columns.sql বলে:
  revoke select (email, bkash_number, nagad_number, student_id, student_id_card_url)
  on public.profiles from authenticated;

কিন্তু live DB বলে:
  authenticated | SELECT | avatar_url, bkash_number, created_at, email, full_name,
                           gender, id, is_verified, locale, nagad_number, phone,
                           role, student_id, student_id_card_url, university,
                           university_id, verification_status     ← সব ১৭টি column
```
তুলনায় `anon`-এর grant ঠিক আছে (১২ column, allowlist অনুযায়ী) — অর্থাৎ
20260702170000 apply হয়েছে, **20260702180000 হয়নি বা পরে undo হয়ে গেছে**।
`supabase_migrations.schema_migrations`-এ দুটোরই কোনো record নেই।

**বাস্তব attack:** যেকোনো verified student login করে
`GET /rest/v1/profiles?select=email,phone,bkash_number,nagad_number,student_id,student_id_card_url`
— RLS policy `"public can view profiles"` এর `qual: true`, তাই পুরো user
base-এর financial + contact PII একটি request-এ।

**Severity:** Critical — mass PII + mobile-money account harvesting
(bKash/Nagad number + নাম + phone = social-engineering-এর সম্পূর্ণ kit)।

**Fix:** revoke পুনরায় apply করা, এবং drift যাতে আর না হয় সেজন্য
P1-1 (migration reconciliation) করা। দীর্ঘমেয়াদে একটি `public_profiles`
view রাখা উচিত যেটায় শুধু public column গুলো থাকবে — column-grant দিয়ে
"নিজের row-তে সব, অন্যের row-তে কিছু" express করা Postgres-এ সম্ভব নয়।

### P0-5 · যেকোনো user অন্যের listing-এর ছবি মুছে বা বদলে দিতে পারে

**কোথায়:** `storage.objects` policies

**প্রমাণ:**
```
"Authenticated users can update room images" | UPDATE | using (bucket_id = 'room-images')
"Authenticated users can delete room images" | DELETE | using (bucket_id = 'room-images')
"Allow authenticated uploads 1l4cebn_0"      | INSERT | with_check = TRUE   ← যেকোনো bucket!
```
কোনোটিতেই owner/room-owner check নেই। `content-images` bucket-এর policy
(Sprint 4-এ migration দিয়ে লেখা) সঠিকভাবে owner check করে — কিন্তু
পুরোনো dashboard-এ বানানো policy গুলো করে না।

**বাস্তব attack:** যেকোনো verified student প্রতিযোগীর room-images মুছে
দিতে পারে (listing defacement), অথবা `with_check = true` policy দিয়ে
যেকোনো bucket-এ যেকোনো path-এ যেকোনো MIME/size-এর file আপলোড করতে পারে —
কোনো bucket-এ size বা mime limit নেই, তাই এটি unbounded storage-cost DoS।

**Severity:** High → Critical (business impact: marketplace vandalism)

**Fix:** তিনটি policy drop করে owner-scoped policy দিয়ে replace করা
(`content-images`-এর pattern অনুসরণ করে), সব bucket-এ size + mime limit।

### P0-6 · Message forgery — একজন user অন্যের নামে message বানাতে পারে

**কোথায়:** `messages` UPDATE policies

**প্রমাণ:**
```
messages_own_update           | UPDATE | using ((auth.uid()=sender_id) OR (auth.uid()=receiver_id)) | with_check = NULL
participants can update messages | UPDATE | একই                                                    | with_check = NULL
```
`WITH CHECK` না থাকলে Postgres `USING` expression-টিকেই check হিসেবে
ব্যবহার করে। তাই একজন participant row-টির **যেকোনো column** বদলাতে পারে,
যতক্ষণ সে নিজে sender বা receiver থাকে।

**বাস্তব attack:** A, B-র কাছ থেকে একটি message পেয়েছে।
`PATCH /rest/v1/messages?id=eq.<msg>` body `{"content": "আমি ৫০০০ টাকা
পাঠিয়েছি, room টা confirm করো"}` → B-র পাঠানো message-এর লেখা বদলে গেল,
কিন্তু sender হিসেবে B-ই থাকল। আরও খারাপ: `receiver_id` নিজের রেখে
`sender_id` **যেকোনো তৃতীয় ব্যক্তির** id করে দেওয়া যায় (check তখনো pass
করে, কারণ সে receiver) → সম্পূর্ণ জাল conversation তৈরি।

Booking dispute বা harassment report-এ chat log-ই একমাত্র প্রমাণ — সেটি
tamper-able হওয়া মানে moderation system-এর ভিত্তি নেই।

**Severity:** High — impersonation, evidence tampering।

**Fix:** UPDATE policy-কে শুধু `is_read` column-এ সীমিত করা (এটাই একমাত্র
বৈধ update, `inbox/[userId]/page.tsx`), এবং receiver-only করা। Content
edit দরকার হলে আলাদা `edited_at` সহ sender-only column-restricted পথ।

### P0-7 · Tenant নিজের booking-এর hold অনির্দিষ্টকাল বাড়াতে পারে

**কোথায়:** `bookings` UPDATE policies + `guard_booking_status_transitions`

**প্রমাণ:** trigger শুধু `status` column পাহারা দেয়
(`if new.status is distinct from old.status`)। কিন্তু policy চারটি
(`bookings_user_update`, `tenant or owner can update booking`,
`booking participants can update`, `Room owners can update bookings`)
সবগুলোতেই `with_check = NULL` এবং কোনো column restriction নেই।

**বাস্তব attack:** Tenant `PATCH /rest/v1/bookings?id=eq.<mine>` body
`{"expires_at": "2099-01-01"}` → ২৪ ঘণ্টার hold চিরস্থায়ী হয়ে গেল।
`expire_stale_bookings()` cron আর কখনো এই booking ধরবে না, seat চিরকাল
আটকে থাকবে। একইভাবে pending booking-এ `seats` বাড়িয়ে পুরো room দখল করা
যায় (owner confirm করলে)। `move_in_date`-ও পরে বদলানো যায়, owner-কে না
জানিয়ে।

**Severity:** High — inventory lockup, marketplace integrity।

**Fix:** trigger-টিকে সম্প্রসারিত করে immutable column list পাহারা দেওয়া
(`room_id`, `user_id`, `seats`, `expires_at`, `created_at` — service_role
ছাড়া কেউ বদলাতে পারবে না), অথবা duplicate policy গুলো drop করে একটিমাত্র
column-scoped policy রাখা।

**কোথায়:** `public.get_email_by_student_id(text)`

**প্রমাণ:** `SECURITY DEFINER`, `proacl: anon=X | authenticated=X`,
কোনো rate limit নেই। Login flow-এর জন্য দরকারি, কিন্তু এটি একটি
open enumeration endpoint।

**বাস্তব attack:** বাংলাদেশি student ID-র format বেশ predictable
(যেমন `২২-৪৬৫৩৩-১`)। ব্রুট-ফোর্স করে কোন ID গুলো registered তা বের করা যায়,
এবং প্রতিটির email পাওয়া যায় → targeted phishing + credential stuffing-এর
লক্ষ্যতালিকা।

**Severity:** High

**Fix:** এই lookup-টিকে একটি rate-limited API route-এর পেছনে নেওয়া
(`/api/auth/resolve-student-id`, Upstash দিয়ে IP-ভিত্তিক limit), এবং
function থেকে `anon` grant তুলে service_role-only করা। Login form-এর
error message দুটিও একরকম করা ("Invalid credentials") যাতে
"Student ID not found" আলাদা signal না দেয়।

### P1-2 · Duplicate ও stacked permissive policy (advisor: 144 hit)

`bookings`-এ ৪টি একই রকম INSERT policy, ৪টি SELECT, ৪টি UPDATE।
`messages`-এ ৪টি INSERT, ৩টি SELECT, ৩টি UPDATE। `rooms`-এ ৩টি DELETE,
৩টি INSERT, ৩টি UPDATE। `profiles`-এ ৩টি INSERT, ৩টি UPDATE।

এটি ঠিক সেই footgun যা `20260702160000_remove_redundant_rooms_visibility_policies.sql`
`rooms`-এর SELECT-এ ধরেছিল: **Postgres সব permissive policy OR করে**, তাই
একটি সঠিক সংকীর্ণ policy-কে একটি ভুলে যাওয়া চওড়া policy নীরবে বাতিল করে
দেয়। SELECT-এ ঠিক করা হয়েছিল, INSERT/UPDATE/DELETE-এ হয়নি।

দ্বিগুণ ক্ষতি: প্রতিটি permissive policy প্রতি row-তে evaluate হয় →
সরাসরি performance খরচ।

**Fix:** প্রতিটি table-এর প্রতিটি command-এ **ঠিক একটি** policy রাখা।
এটি Hard Rule 1 অনুযায়ী before/after diff সহ approve করাতে হবে।

### P1-3 · `auth.uid()` per-row evaluate হচ্ছে (advisor: 78 hit)

### P1-4 · ভুয়া review-এর কোনো বাধা নেই

**Trade-off যেটা আপনাকে জানাতে চাই:** Sprint 0-এর P0-2 fix (bucket
private) করলে admin verification screen-এ ID card preview সাময়িকভাবে ভাঙবে
— signed-URL flow তৈরি না হওয়া পর্যন্ত। দুটি পথ আছে:

- **(ক) একসাথে করা** — bucket private + signed URL একই sprint-এ। ~৪ ঘণ্টা,
  কোনো downtime নেই। **আমার সুপারিশ এটাই।**
- **(খ) আগে bucket বন্ধ, পরে signed URL** — breach এখনই বন্ধ হয়, কিন্তু
  admin কয়েক ঘণ্টা verify করতে পারবে না। যদি মনে করেন এই মুহূর্তেই
  exposure বন্ধ করা সবচেয়ে জরুরি, তাহলে এটি।

কোনটি নেব, জানালেই শুরু করব।
